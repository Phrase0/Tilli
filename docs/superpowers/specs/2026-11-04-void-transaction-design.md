# 交易作廢 設計文件

2026-11-04，與使用者討論確定。`〔我的決定〕` 標的是使用者沒特別指定、由設計者先決定的部分。取代 `FEATURE_PLAN_V1.md` Backlog 裡 2026-10-28 的「交易作廢」草案。

## 1. 為什麼做、做什麼

攤商在攤位上剛結完帳，客人當場反悔、或自己按錯商品／數量，旁邊可能還有客人在排隊。目前結帳寫下去就改不了，報表、庫存都會一直帶著這筆錯誤。

這次讓攤商可以把一筆交易**整筆作廢**：原交易保留不動、標成已作廢，報表不再計入；庫存要不要加回去由攤商當下決定（退回的食物常常不能再賣）。

### 目標
- 交易明細可以作廢該筆交易，必選原因與庫存處理方式，二次確認後生效。
- 作廢後所有營收／筆數／銷量統計都排除這筆，但交易紀錄仍看得到並標示「已作廢」。
- 選「回流」時，庫存精確加回這筆交易當初扣掉的數量，並留下庫存異動紀錄。

### 非目標
- 部分退貨（只退其中幾項）：不做、也不預留。客人只退部分時，整筆作廢再重結剩下的商品。
- 作廢後還原：不做。要重來就新增或補記帳。
- 收銀頁「作廢上一筆」捷徑：不做，入口只在交易明細。
- 報表上顯示「作廢 N 筆／作廢金額」統計：留給查看分析頁重新設計。
- 作廢紀錄的雲端同步：併入之後「新欄位雲端同步」那一批。
- 交易明細 CSV 的作廢狀態欄位：留給下一批 CSV 重新設計。

### 反目標（做出來但算失敗）
- 任何一處營收或筆數仍把作廢交易算進去（例如場次列表、日曆的摘要和查看分析對不起來）。
- 修改到原交易的任何欄位（交易是流水帳快照）。
- 同一筆交易被作廢兩次、或回流兩次。
- 回流數量和當初扣掉的數量不一致（尤其是套餐成員）。
- 誤觸就作廢（沒選原因／庫存處理、沒經過確認框就生效）。

## 2. 使用者決定

1. 入口**只在交易明細**。
2. **只做整筆作廢**。
3. 原因**必選**，四選一：輸入錯誤／客人取消／退貨／其他，用**選取（Picker，跟編輯庫存一樣）**，不用 tag；補充文字選填，提示字「請輸入作廢原因」，一律顯示。
4. 庫存「回流／不回流」**沒有預設值，必選**；兩個必選都選了，作廢按鈕才可按。
5. 按下作廢後**再跳一個確認框**才生效。
6. **任何交易都能作廢**：不限場次是否結束、不限日期。
7. 交易紀錄每日標題的「N 筆交易」**只算有效交易**，當日總額也不算作廢的。
8. 作廢資料**另存成一筆作廢紀錄**（新實體），原交易完全不改。
9. 沿用草案：只能作廢一次、不能還原；作廢的交易從營收、銷量、類別、折扣統計排除，排除邏輯集中一處；有交易的商品仍鎖定（作廢不解除）。

## 3. 資料

### 3.1 新實體：作廢紀錄

新增 CoreData 實體（名稱交給建構者，例如 `CDTransactionVoidEntity`），流水帳、只新增不修改：

| 欄位 | 分類 | 說明 |
|------|------|------|
| `id` | R | |
| `transactionId` | R | 被作廢的交易 |
| `eventId` | R | 方便依場次載入 |
| `voidedAt` | S | 作廢時間 |
| `reason` | S | 四選一的 raw value |
| `note` | S | 補充文字，選填 |
| `restocked` | S | 是否回流 |
| `updatedAt` / `userId` / `syncStatus` | M | 比照 `CDInventoryChangeEntity` |

- 要在 `ARCHITECTURE.md` §4 新增這個實體的分類表，並跑 `scripts/check_field_classification.py`。
- `SYNC_ARCHITECTURE_V2.md` 的流水帳列表補上這個實體（同步仍是取聯集；不在這次實作同步）。
- 一筆交易最多一筆作廢紀錄。寫入前檢查已存在就**拒絕**（守衛只拒絕，不靜默略過）。若之後同步出現兩筆，以 `voidedAt` 最早的為準〔我的決定，只需寫在文件，這次不用實作同步〕。

### 3.2 「是否作廢」的判斷只有一份實作

新增一個共用計算元件（名稱交給建構者），輸入交易與作廢紀錄，回答「這筆交易作廢了嗎、作廢紀錄是什麼」以及「有效交易清單」。登記到 `CONVENTIONS.md`「共用計算元件」清單，並寫明「不准再出現」的寫法（例如在 VM 裡自己比對 transactionId）。

目前讀交易的地方（2026-11-04 盤點），每一處都要走這個元件：

| 位置 | 用途 | 作廢的處理 |
|------|------|-----------|
| `EventDataSource.reload()` / `transactions(in:)` / `transactionSummary` | 場次工作區所有報表 | 報表拿有效交易；交易紀錄需要全部（含作廢）＋作廢狀態 |
| `SalesAnalyticsViewModel`、`ProductPerformanceViewModel` | 營收、銷量、類別、折扣、商品成效 | 排除 |
| `TransactionHistoryViewModel` | 交易紀錄列表、總額 | 列表顯示全部；總額與筆數只算有效 |
| `EventsViewModel.transactionSummary`、`EventsCalendarViewModel.transactionSummary` | 場次列表、日曆的筆數／總額（直接走 Repository，不經 `EventDataSource`） | 排除 |
| 交易明細 CSV（`generateCSVContent`） | 匯出 | 排除〔我的決定〕 |
| `TransactionIndex`（商品／類別鎖定）：`EventDataSource.reload()`、`AddEventViewModel`（第 146 行附近）、`AddNewProductViewModel.updateDataManagers`（第 256 行附近）、`ProductRepository` | 鎖定 | **不排除**（作廢不解鎖） |
| `AddEventViewModel.getTransactionDateRange` | 編輯場次的日期限制 | **不排除**（避免場次日期被改到切掉作廢交易）〔我的決定〕 |

註：`EventDataSource.transactionSummary` 目前沒有呼叫端；實作時可順手移除或改成有效交易，交給建構者。交易編號一律用 `TransactionModel.displayNumber`（格式 `TXN` + UUID 前 8 碼大寫，例如 `TXN1A2B3C4D`），不要自己拼。

`EventDataSource` 對外怎麼提供「全部」與「有效」兩種清單交給建構者，但報表 VM 預設拿到的必須是有效交易，不能靠每個 VM 記得過濾。

**場次列表與日曆不改走 `EventDataSource`**（與使用者確認）：`EventDataSource` 是單一場次的完整快照（商品、類別、全部交易、全部庫存異動），由工作區建立、三個分頁共用；列表頁一次顯示多個場次、只需要每場的筆數與總額，為每張卡片建一個會整包載入用不到的資料，生命週期也不對。做法：
- `EventsViewModel` 與 `EventsCalendarViewModel` 目前各寫一次 `fetchTransactions(forEventId:).summary`，收斂成**一個**共用函式（「某場次的有效交易摘要」，位置交給建構者，例如 Repository 方法），內部經上述作廢判斷元件。
- `EventDataSource.reload()` 載入交易時一併載入該場次的作廢紀錄，交給同一個元件。
- 兩條路徑共用同一個作廢判斷元件與同一個 `summary` 定義，數字必然一致；要有測試證明同一份資料兩邊算出相同筆數與總額。

## 4. 作廢流程

UI 草圖已與使用者確認（visual companion：`.superpowers/brainstorm/` 下的 `void-flow.html` 與 `void-sheet-v2.html`，作廢視窗以 v2 為準）。

依 `DESIGN.md`：警示紅只能用在文字，不能當按鈕底色，所以下文的「作廢」按鈕都是**靜謐填色底＋警示紅字**（`button-destructive`），不可按時字變灰。

1. 交易明細最下方（優惠明細之後）：「作廢交易」按鈕（已作廢的交易不顯示）。
2. 按下 → 作廢視窗（sheet，導覽列左上「取消」、標題「作廢交易」），**系統 Form 樣式，與編輯庫存（`AddNewProductView` 的庫存原因）一致**：
   - 第一區：交易編號（小字、muted）與金額（大字）〔我的決定〕。
   - 「作廢原因」區：
     - 「原因」一列，系統 `Picker`（點了跳選單）四選一：輸入錯誤／客人取消／退貨／其他。**沒有預設**，未選時顯示「請選擇」（selection 用 optional）。
     - 下一列是補充文字 `TextField`，提示字「請輸入作廢原因」，選填；**不論選哪個原因都顯示**（使用者決定，和編輯庫存只在「其他調整」才出現不同）。
   - 「庫存」區：分段控制「回流／不回流」，**沒有預設**（兩段都未選中）；下方說明「回流：把這筆交易的商品數量加回庫存」。
   - 最下方「作廢」按鈕：原因與庫存都選了才可按。
3. 按「作廢」→ 系統確認框：標題「作廢 TXN1A2B3C4D（$350）？」，內文「作廢後無法還原。」並多一行「庫存：回流／不回流」〔我的決定〕；按鈕「取消」／「作廢」（destructive）。
4. 確認後寫入（第 5 節），關閉視窗，交易明細切到已作廢狀態；返回交易紀錄時列表已更新（沿用 `onAppear` + 重新載入）。

寫入邊界在 VM（比照付款 VM 建立交易前的保護）：VM 再檢查一次「已作廢就拒絕」「原因與庫存方式都有值」，不依賴 View 的按鈕 disabled。

## 5. 寫入內容

作廢的寫入做成純函式（比照 `CheckoutRecorder`），輸入交易、它的庫存異動、選項，輸出要寫的作廢紀錄、庫存異動、商品庫存更新；VM 負責呼叫 Repository。

- **作廢紀錄**：一筆（3.1）。
- **不回流**：只寫作廢紀錄，庫存完全不動。
- **回流**：
  - 對這筆交易當初的每一筆「銷售出庫」異動（`reason == .salesOut` 且 `transactionId` 相同），新增一筆反向異動：`change` 為正的相同數量、`reason` 為**新增的庫存異動原因「作廢回流」**（使用者決定）、`transactionId` 為這筆交易、`bundleId`／`bundleName` 照抄、`customReason` 留空。
  - 「作廢回流」是增加類原因，和「銷售出庫」一樣**只由系統自動產生**：不出現在手動編輯庫存的原因選項（`InventoryChangeReason.increaseReasons`、`availableReasons(for:)` 都不含它）；顯示名稱走 `Localizable.xcstrings`。
  - 商品庫存加回對應數量（同一商品多列時累加）。
  - 以「當初的異動」為準而不是重新從 `items` 算，確保加回的正好是扣掉的〔我的決定〕。附註：結帳扣庫存會 clamp 到 0（`CheckoutRecorder.stockUpdates`），理論上「庫存不足仍賣出」時回流會加回比實際扣掉更多；但收銀頁加入購物車時已擋超過剩餘庫存、購物車超量也會進失效通知，實務上不會發生，不額外處理〔我的決定〕。
  - 商品已下架仍照樣加回庫存。
- 寫入順序與失敗處理交給建構者，但不能出現「有作廢紀錄卻只回流一半」而沒有任何錯誤提示。

## 6. 作廢後的顯示

- **交易明細**（草圖已確認）：最上方加一張「已作廢」卡片（左側警示紅細條＋紅字標題「已作廢」），列出作廢時間、原因、說明（有才顯示）、庫存（已回流／未回流）；原本的資訊、商品、優惠明細照常顯示（快照不變）；不再出現「作廢交易」按鈕。
- **交易紀錄卡片**（草圖已確認）：整張變淡、金額加刪除線、交易編號旁加「已作廢」標籤（靜謐填色底＋紅字）；位置照時間不動，仍可點進明細。
- **每日標題**：總額與「N 筆交易」只算有效交易。若某天全部作廢，標題顯示 $0、0 筆，卡片仍列出〔我的決定〕。
- **庫存異動列表**（`InventoryProductCard.changeRow`）：原因標籤顯示「作廢回流」即可；列表本來就沒有交易編號欄，**不新增**（使用者決定）。
- **庫存 CSV**（`InventoryViewModel` 約第 295 行）：原因欄為「作廢回流」；交易編號欄目前只在 `.salesOut` 有值，改成銷售出庫與作廢回流都帶出交易編號。
- **查看分析各頁、場次列表、日曆**：數字直接排除作廢交易，不另外標示。

外觀對照 `DESIGN.md` token，不自創；「整張變淡」的透明度等細節交給建構者，但要確保深色模式下仍可讀。

## 7. 限制

- 不改 `TransactionModel` 與 `CDTransactionEntity` 的任何欄位。
- 金額一律 `MoneyHelper`。
- 使用者可見文字一律 `Localizable.xcstrings`（lowerCamelCase key，上方註解中文原文）。
- 場次工作區內經 `EventDataSource`，不另外呼叫 Repository（作廢寫入由明細 VM 經注入的 Repository 完成，寫完觸發重新載入；具體注入方式交給建構者）。
- 交易明細目前是唯讀 VM（`TransactionDetailViewModel` 只吃 `TransactionModel`），需要擴充成能讀作廢狀態與執行作廢；維持一頁一 VM。
- 新增 `InventoryChangeReason` case 會影響 `isIncrease`／`isDecrease` 等 switch 與既有測試，要一併補齊。`ARCHITECTURE.md` §4 `CDInventoryChangeEntity.transactionId` 的說明「僅銷售出庫時有值」要改成「銷售出庫與作廢回流時有值」。
- 測試：作廢判斷元件、寫入純函式（含套餐成員、同商品多列、不回流、重複作廢被拒）、報表排除、場次列表／日曆摘要排除、「作廢回流」不在手動原因選項，都要有單元測試。CoreData fixture 直接建 entity。

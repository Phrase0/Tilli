# 組合與套餐 設計文件

日期：2026-10-27　分支：`feature/Bundles`
取代／修訂：`FEATURE_PLAN_V1.md` §8（組合優惠與套餐）、§13 #1 #3 #4。對照見文末「與計畫書 §8 的差異」。

## 1. 為什麼做、做什麼

Tilli 是給台灣市集攤商用的 iOS POS App（SwiftUI + CoreData + Firebase，未上架、沒有真實使用者）。攤商常有兩種優惠：

- **套餐**：固定內容、固定價格，例如「下午茶套餐 = 大福＋抹茶＋紅豆，100 元」。收銀時像商品一樣**直接點選**。
- **組合**：湊數量就算特價，例如「大福任選三個 100」（大福單價 40）。收銀時**不用特別操作**，依點選的商品數量自動換算。

本文件還包含一塊與之相關、但可獨立進行的 **收銀頁互動調整**（§8）：商品增減改成 Uber Eats 式，訂單摘要可增減移除商品，折扣與組合合併顯示。

### 目標
- 套餐能在收銀頁一點加入，缺貨時清楚灰掉並說明原因。
- 組合在收銀時完全不增加操作步驟；結帳時看得到折抵，也能取消。
- 多重優惠下營收仍然對得上：銷售分析總營收 == 商品績效加總 == 類別分析加總（測試 R2 不得退步）。
- 套餐與組合的設定隨「複製場次」一起複製。

### 非目標（這一輪不做）
- 「套餐／組合成效」報表（賣了幾份、折抵多少）——使用者明確說先不加。
- 有選擇的套餐，例如「餐點＋任一飲品」、補差價。**不預留欄位**；之後需要時改 `BundleModel` 即可（內容是 JSON，不用 CoreData 遷移）。
- 組合的最佳化（算全域最低價）。
- 套餐成員可設數量（A×2）；組合以「類別」為候選。
- 組合的照片。

### 反目標（技術上做出來但算失敗）
- 收銀變慢，或每筆交易多一個步驟。
- 套餐裡的商品又被組合重複計算（同一個商品吃兩次優惠）。
- 報表營收對不上。
- 守衛靜默改做別的事（專案規則：守衛只准拒絕）。

## 3. 資料模型

存放：`CDEventEntity.bundlesData: Binary`（`[BundleModel]` 的 JSON），與 `discountsData` 同一模式；不新增 entity。

```swift
struct BundleModel: Identifiable, Codable, Hashable {
    var id: UUID
    var name: String
    var price: Decimal              // 套餐價／組合價
    var mode: BundleMode
    var productIds: [UUID]          // fixed: 成員（各 1 個）；chooseAny: 候選商品
    var isDisabled: Bool            // 「下架」
    var imageURL: String?           // 只有套餐使用；本機圖見下
    // 建立時間／顯示順序：由建構者決定（§11）
}
enum BundleMode { case fixed; case chooseAny(count: Int) }
```

- 移除計畫書 §8.2 的 `sortOrder`（套用順序改由系統自動決定，見 §5.3）。
- **照片**（僅套餐、選填）：沿用商品的做法——本機存檔、JSON 內只放 `imageURL`；圖檔**不放進** `bundlesData`（會讓整份場次文件變大）。沒設定照片時，卡片顯示與無照片商品相同的預設樣子。
- 解碼要容錯：缺欄位給預設值（`init(from:)`），與 `SummaryItemModel` 同做法。
- **`SummaryItemModel` 另外新增兩個儲存欄位**（在 `itemsData` JSON 內，無 CoreData 變更；缺 key 時解碼為預設值，沿用第 4 批的 `init(from:)`）：
  - `bundleDiscount: Decimal`（預設 0）：`allocatedDiscount` 中**來自套餐／組合價差額**的部分（計畫書 §7.3 的步驟 ②）。整筆折扣分到的部分 = `allocatedDiscount − bundleDiscount`。由 `RevenueAllocator` 寫入。
  - `bundleKind: BundleKind?`（`.fixed` / `.chooseAny`，預設 nil）：快照這一列屬於套餐還是組合。套餐刪除後歷史明細仍要知道該把它顯示成「套餐價」還是「組合折抵」。
  - 用途：讓交易明細能還原成與訂單摘要相同的樣子（見 §7）；也讓日後的「套餐／組合成效」報表不必再改 schema。
- 「可不可賣」是**算出來的**，不存（`isAvailable`，見 §6），與 `ProductAvailability` 同原則。

## 4. 畫面與操作

參考 mockup（已核可）：`.superpowers/brainstorm/*/content/` 的 `bundle-screens-v2.html`、`cart-pos-v3.html`、`cart-bundle-v2.html`。

### 4.1 管理商品頁
- chip 列：`全部｜套餐｜組合｜類別…`。**「組合」chip 只出現在管理商品頁**；收銀頁只有「套餐」chip。
- 「套餐」「組合」各一個區塊（與類別區塊並列），套餐列有縮圖、名稱、價格、成員摘要；組合列有名稱、價格、「任選 N 個」與候選摘要。
- 每一列右側「⋯」選單：**編輯／下架／刪除**（已下架者顯示「上架」）。表單內沒有停用開關與刪除鈕。
- 右下 `＋`：場次內**還沒有任何商品**時直接進「新增商品」；有商品後從 `＋` 旁彈出選單：**新增商品／新增套餐／新增組合**。
- 缺貨／成員下架的套餐與組合列要顯示警告原因（例如「抹茶 缺貨」）。

### 4.2 新增／編輯表單
- **套餐**：照片（選填）、名稱、價格、成員（從場次商品勾選，各 1 個）。價格欄下常駐「原價合計 $X，套餐價省 $Y」（即上限），超過時紅字緊接在下方。
- **組合**：名稱、價格、任選幾個（N）、候選商品（勾選）。價格欄下常駐「上限 $X（N × 最便宜的 $Y）」。
- 驗證（**有任何錯誤儲存鈕就變灰**；錯誤即時顯示在欄位下方，只顯示「填了但填錯」的紅字，還沒填完只讓儲存變灰）：名稱不可空白、同場次內套餐／組合名稱不可重複；價格 > 0；套餐成員 ≥ 2；組合 N ≥ 2 且候選 ≥ 1（候選只有 1 個商品是合法的，即「同一款買 N 個」）。
  - **套餐價 ≤ 成員原價合計**（否則攤提會出現負折扣）。
  - **組合價 ≤ N × 候選商品中最低的單價**（無論客人湊哪幾個，都不會比原價貴）。
  - 價格等於上限（沒有優惠）→ 允許，只提醒「這個價格沒有優惠」。
- 成員／候選只能選現有商品（含已下架者顯示為灰，可選但標示）；細節由建構者決定。

### 4.3 編輯、下架、刪除規則
- **編輯**：任何時候都能改名稱、價格、成員、N、照片。歷史交易存的是快照，不受影響（與商品「有交易後鎖定」不同，因為套餐／組合不是報表分組的依據）。
- **下架**：`isDisabled = true`；收銀頁不顯示該套餐（組合則不再自動套用）；可「上架」恢復。
- **刪除**：**不論有沒有交易紀錄都能刪**，刪除前確認。歷史交易靠快照（`bundleId`、`bundleName`）仍可顯示。
- **刪除商品時**，若它被任何套餐或組合引用：**拒絕並列出是哪幾個**（誠實失敗，不自動從套餐移除成員）。使用者須先改套餐／組合或刪除它們。（商品原本「有交易只能下架」的規則不變。）
- **商品改價**時，若會讓任何套餐或組合違反上述價格條件：**拒絕並列出是哪幾個**（與刪除商品被引用同一規則；改價本來就只有在沒有交易時才可能）。
- **下架商品**不被擋：相關套餐灰掉並顯示原因；相關組合只是候選不計入。商品上架回來即自動恢復。

### 4.4 複製場次
複製場次時（`EventRepository.duplicateEvent` 會複製**所有**類別與商品，含已下架者），套餐與組合**一起複製**，且 `productIds` 必須**重新對應到新場次複製出來的商品 id**（商品複製時會產生新 id，不可仍指向舊場次的商品）。套餐照片一併帶過去。

### 4.5 收銀頁（套餐）
- 套餐卡片點選即加入購物車；與商品共用新的增減元件（§8.1）。
- **購物車只顯示一行**「下午茶套餐 × 1」，可增減份數、移除。拆成成員只發生在結帳寫入時（扣庫存、攤提營收）。
- 套餐成員任一缺貨或下架 → 卡片灰掉並顯示原因，不可點。
- 購物車內已有的套餐在回到收銀頁時若失效 → 見 §9.1 第 5 點（通知＋確定後清除該行）。

## 5. 行為

### 5.1 套餐（`.fixed`）
- 一份套餐 = 每個成員各 1 個、總價 = 套餐價。
- 結帳寫入時：套餐展開成成員的 `SummaryItemModel`（帶 `bundleId`、`bundleName`），套餐價與成員原價合計的**差額**以 `RevenueAllocator` 的 `BundleDeduction` 攤到成員（按各自原價比例；捨入規則沿用第 4 批）。例：大福 40、抹茶 60、紅豆 20（合計 120）賣 100，差額 20 → 實收 34／49／17。
- 庫存：每個成員各扣 1 份，產生 N 筆 `InventoryChange`，每筆帶 `bundleId`、`bundleName`（新增欄位）。

### 5.2 組合（`.chooseAny(count: N)`）
- 不出現在收銀頁，**自動套用**。
- 數量計算**只算購物車裡單點的商品**；屬於套餐的成員**不計入**組合候選（同一商品不吃兩次優惠）。
- 候選商品已下架者不計入；組合本身不因此失效。
- 套用步驟：把符合候選的單點商品展開成單位 → 依**單價由高到低**排序 → 每 N 個一組套用組合價 → 不足 N 個的照原價。同一個單位只會被一個組合使用。
- 候選可為單一商品（「大福三個 100」＝大福 ×3）或多款混搭（任三款大福 100）。

### 5.3 多個組合重疊
同一商品可屬於多個組合。**由系統自動決定套用順序，不給使用者排序**：**每件平均價（組合價 ÷ N）較低的先套用**（例：五個 150 = 30/件，先於三個 100 ≈ 33.3/件）。這是貪婪、可預測的規則，**不做全域最佳化**。同分時的決勝規則由建構者決定。

### 5.4 結帳時取消組合
- 訂單摘要顯示自動套用的組合；可對**該組合規則**取消，**只對這一筆交易有效**，可「恢復」。
- 取消後，其餘折扣依新的小計重算。

### 5.5 與整筆折扣的順序
沿用計畫書 §7.3：**組合／套餐差額 → 百分比折扣 → 減額折扣 → 捨入差額**。範例：小計 340，組合 −40，10% −30，−25 → 總計 245；取消組合後：10% −34，−25 → 281。

### 5.6 庫存與可販售
- 套餐最多可賣份數 = 各成員**剩餘庫存**（扣掉購物車已佔用）中最少的那個。例：大福剩 1、抹茶 5、紅豆 5 → 最多 1 份。
- **雙向佔用**：購物車裡單點的大福佔用庫存，會減少可加的套餐份數；反之，加了套餐也會減少可單點的大福。
- 可用性是計算值：`isAvailable(products:…)`，未下架且所有成員存在、未下架、庫存足夠才可賣；收銀頁與管理頁要顯示**原因**。

## 7. 報表與交易明細的影響（已檢查現有程式碼）

**不會壞（因為套餐在結帳時展開成成員、差額已攤進 `allocatedDiscount`）：**
- 銷售分析總營收（用 `transaction.totalAmount`）、商品績效與類別分析營收（Σ `actualRevenue`）——R2 不退步，測試要補含套餐／組合的案例。
- 銷量與平均單價：套餐成員各算賣出的數量；平均單價用原價總額 ÷ 銷量，不受影響。
- `TransactionIndex`：成員有 `productId`，「商品有交易就鎖定」的判斷照常運作。

**會跑掉或不對（需要修）：**
1. **歷史交易明細（`TransactionHistoryView`）**：
   - 「共 N 項商品」用 `items.count`：套餐展開成 3 個成員會變 3 項、組合拆列也會增加。
   - 展開明細列出成員的**原價**小計，加上目前只顯示「整筆折扣」標籤，**套餐／組合折抵沒有任何地方顯示**，所以小計加起來 − 整筆折扣 ≠ 總金額，看起來像算錯。
2. **交易明細 CSV（`TransactionHistoryViewModel.generateCSVContent`）**：現況就有問題（見下），加入套餐／組合後更對不起來；整份重新設計**延後**到套餐之後。
3. **「折扣最多的商品」洞察與商品績效的折扣欄位**：用 `allocatedDiscount`，現在會**混入套餐／組合差額**。語意上變成「優惠最多的商品」。
4. **庫存異動紀錄與匯出**：套餐會產生每個成員各一筆異動，數量正確，但需要顯示來源套餐（見 §9.1 第 7 點）。

**修法（使用者已選定版本 B）：新增 `bundleDiscount`、`bundleKind` 兩個快照欄位（§3），讓歷史明細還原成與訂單摘要相同的版面。**
- 還原規則（單一共用元件計算，不在各 View 重寫）：
  - 套餐顯示為**一行**：名稱、份數、套餐價 = Σ 成員 `total` − Σ 成員 `bundleDiscount`；成員名稱以小字列出（`bundleKind == .fixed`）。
  - 組合涵蓋的商品列正常顯示原價，旁邊加「含組合」小標；各組合的折抵 = 同一 `bundleId` 各列 `bundleDiscount` 之和，在優惠明細中**各一行**（`bundleKind == .chooseAny`）。
  - 整筆折扣各一行（百分比、減額）取自 `appliedDiscounts`；小計 = 商品列（套餐以套餐價）加總；總計 = `totalAmount`，折扣前金額劃線，並顯示「共省」。
  - 恆等式要測：小計 − 各組合折抵 − 各整筆折扣 = 總計（捨入差額已在結帳時由 `RevenueAllocator` 處理）。
- 「共 N 項商品」：同一套餐的成員算 1 項。
- **CSV（交易明細匯出）延後**：使用者決定整份 CSV 要重新設計，排在套餐與「交易作廢」之後另案處理，**本批不改 CSV**。現況的問題（總金額每列重複、整單折扣是文字不是金額、沒匯出實際營收）已記在 `FEATURE_PLAN_V1.md` Backlog。本批新增的 `bundleName`、`bundleDiscount`、`bundleKind` 已足夠讓之後的 CSV 使用。
- 折扣洞察「折扣最多的商品」與商品績效折扣欄位：維持用 `allocatedDiscount`，語意視為「優惠」，必要時只調整文案。

## 8. 收銀頁互動調整（可與 §3–7 分開做）

### 8.1 商品／套餐增減元件（Uber Eats 式）
- 預設只有一個 `＋`；點了展開成 `－ 1 ＋`；點其他地方收合成圓形，只顯示數量（再點圓形可再展開）。數量為 1 時按 `－` 即移除；庫存上限沿用現行判斷。
- **列表版**：元件在卡片右下。**格狀版**：元件疊在**圖片右下角**（不在文字下方）。兩版都要改。
- 以現有 UI 的顏色與元件風格為準（見 `cart-pos-v3.html`）。

### 8.2 底部總計列
黑色結帳鈕左側顯示金額（折扣前劃線＋折後金額），右側「結帳 →」。折扣挑選 chip（百分比／減額）仍在收銀頁；原本單獨一行的「NT$132 → NT$94」併入此處。

### 8.3 訂單摘要
- 每一行可增減／移除（數量 1 時 `－` 變垃圾桶）；套餐仍一行。
- 被組合涵蓋的商品旁顯示「含組合」小標。
- 總計區改為「優惠明細」：小計、組合優惠（附取消／恢復）、百分比折扣、減額折扣、總計（大字，折扣前劃線，「共省 NT$X」）。取消組合後其餘折扣重算。折扣仍在收銀頁挑選，這裡只顯示。
- 補記帳、現金付款、電子支付維持現有版面。

## 9. 交給建構者決定
- 套餐／組合列表的顯示順序與 `sortOrder` 是否保留（本文件預設不保留）；組合同分決勝規則；`bundlesData` 的 JSON 版本欄位；檔案放置、命名、多語言 key；成員挑選器的細節 UI；「已下架商品是否可被勾選為成員」的具體呈現。
- `InventoryChange.bundleId` 是否只在套餐上設定（本文件預設：只有套餐；組合只在 `SummaryItem` 帶 `bundleId`）。
- 測試設計（至少：攤提恆等式含套餐、組合自動套用與順序、套餐成員不計入組合、庫存雙向佔用、刪除商品被引用時拒絕、複製場次的 id 重新對應、R2 營收相等）。

## 9.1 審查補充：設計者的決定（標記為「我的決定」，請使用者核對）
1. **購物車**：新增明確的行型別（商品行／套餐行），套餐在購物車是獨立一行，不展開。「含組合」標示與組合折抵由純計算元件（與 `DiscountCalculator` 同層級的單一實作）從購物車算出，**不存**。購物車的型別調整（POS／結帳／付款 VM）在範圍內。〔我的決定〕
2. **組合不會讓客人變貴**：由「儲存時擋住」保證（§4.2）以及「商品改價守衛」（§4.3），執行階段不需要再判斷。〔使用者決定〕
3. **取消組合**以組合 `id` 為單位，只對這一筆交易有效；取消後**重新執行**自動套用（把該組合排除），釋放出來的單位可被下一順位的重疊組合使用，其餘折扣重算。〔我的決定〕
4. **組合的 `SummaryItem` 表示**：同一商品「部分被組合涵蓋、部分沒有」時，拆成兩列（一列帶 `bundleId`／`bundleName` 與 `allocatedDiscount`，一列是原價），現有 schema 足夠，不新增欄位。〔我的決定〕
5. **進行中的購物車遇到套餐被刪除／下架／改價／缺貨**：回到收銀頁（`onAppear` 重新載入）時重新驗證；若有失效的套餐，**跳出通知**說明「哪些套餐、為什麼不能結帳」，使用者按下確定後，**只清除這些無法結帳的套餐行**（整行移除），其餘商品保留。不靜默處理：一定先通知、經確定才清。〔使用者決定，取代原本「擋住結帳」〕
6. **複製場次**：不會有成員沒被複製的情況（見 §4.4），只需重新對應 id。〔使用者確認〕
7. 庫存異動紀錄畫面：有 `bundleName` 的異動顯示「來自〈套餐名〉」，細節由建構者決定。〔我的決定〕
8. **交易明細的資料來源**：為了還原成與訂單摘要一致的版面，`SummaryItemModel` 需要**兩個**新欄位（`bundleDiscount`、`bundleKind`），不是先前口頭說的一個；原因是套餐刪除後仍要知道該顯示為套餐價還是組合折抵。〔我的決定，待使用者核對〕
